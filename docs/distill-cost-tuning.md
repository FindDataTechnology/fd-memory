# 蒸馏成本与分片参数：要不要改 CHUNK

> 2026-11-10 结论。数字取自一次生产部署的 `tokens.db.distill_budget` 与
> `distill-scheduler.ts` 的常量。**结论：不改 `CHUNK=2`。**

## 一、现网实测

按日汇总（`distill_budget`，全站）：

| 日期 | tokens | 引擎调用 | tokens/调用 |
|---|---|---|---|
| 2026-11-09 | 2,742,865 | 447 | 6,136 |
| 2026-11-08 | 4,800,434 | 707 | 6,790 |
| 2026-11-07 | 1,162,856 | 123 | 9,454 |

单 owner 最高：`u-aloadtree@gmail.com` 在 2026-11-08 花掉 **3,734,259** tokens / **324 次调用**，
即 **11,525 tokens/次**。

对照常量：

| 常量 | 值 | 位置 |
|---|---|---|
| `CHUNK`（每条引擎调用送几条） | 2 | `src/distill-scheduler.ts` u-root 路径 |
| 单条 summary 上限 | 800 字 | 同上 |
| 单次运行每流派最多取 | 120 条 | `MAX_ITEMS` |
| 日预算 | 400,000 tokens（默认） | `FD_MEMORY_DISTILL_DAILY_TOKENS` |

也就是说：**一次满载运行最多 180 次调用**（handoffs 120 + notes 120，每 2 条一调），
按 11.5k/次计约 **200 万 tokens** —— 这正是 2026-11-08 那个 373 万落在同一量级的原因
（两次满载或一次跨流派的满载）。

## 二、为什么当时会把 CHUNK 定成 2

代码里留了生产探针记录（`src/distill-scheduler.ts` u-root 分支注释）：

> 引擎的抽取输出会在完成度上限处被截断，而**被截断的 JSON 会被吞成空结果**——不报错、
> 0 页。实测 4 条真实交接 → `completion_tokens` 6000 → 静默零产出。2 条一调、summary
> 截 800 字，`completion` 约 4.4k，稳定低于上限。

这是**用调用次数换不丢产出**的取舍：失败形态是静默的（没有错误、没有日志、只是少了几页），
所以不能靠「跑完看一眼」发现。

## 三、结论：不改

三条理由，按证据强度排序：

1. **成本侧的风险已经被另一处修复消除。** 2026-11-10 之前日预算只在运行**开始前**读一次、
   结束时才记账，所以单次长跑能超出上限 9.3 倍。修复后闸门逐片重读账本、每次调用后增量记账，
   单 owner 的单日花费被限定在 `cap + 一次调用` ≈ 400k + 11.5k。把 CHUNK 调大省下的是调用次数，
   而调用次数已经不是风险。
2. **收益侧换来的是静默损失。** 加大分片直接逼近「完成度截断 → 空结果」这个已知失败面，
   而该失败不产生错误信号。用可见的成本换不可见的损失，方向反了。
3. **tokens/调用 ≈ 11.5k 里，能省的大头不在分片。** 每次调用都会重跑一次候选检索
   （`hybridCandidates`，k=8，每条包含最多 2000 字正文）并把它塞进 prompt；同一次运行的
   180 次调用重复了 180 份近似相同的候选上下文。这是比「每条多送几条」更干净的下一个杠杆，
   且不触碰完成度上限。

## 四、下一个杠杆（不在本 change 范围）

按上面的观察，若要继续降本，优先级应为：

1. **同一次运行内复用候选集**（而不是逐片重算重送）—— 省的是 prompt 侧，不碰 completion 上限；
2. 其次是给 `MAX_ITEMS` 与日预算做联合配置（满载运行的上限由两者共同决定，目前没有联动）；
3. 最后才考虑 `CHUNK`，且必须同时给出「加大分片导致完成度截断」的可观测判据（例如空产出率
   或 `llm_calls[].completion_tokens` 接近上限的比例），否则改不动。

## 五、可观测性（已落地）

`/admin/metrics` 的 `distill.recent` 现在给出最近至多 200 次成功运行的分布：
`items / calls / tokens` 的 total、mean、max，tokens 的 p50/p90，以及最后一次运行的四项明细。
失败不计入样本（失败运行没有成本画像）。这让「一次运行是不是吃掉了 120 次调用」
成为可读事实，而不是靠推理。
